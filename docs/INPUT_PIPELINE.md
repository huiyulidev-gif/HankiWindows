# 한키 입력 파이프라인과 실패 지점

이 문서는 공개 0.2.0 소스(`fcbaef2`)를 기준으로 확인한 기존 동작과
0.2.1 호환성 패치의 목표 동작을 구분해 기록한다. 실제 PC방 보안
환경에서 얻은 진단 보고서가 아직 없으므로 특정 보안 제품이나 관리자 권한을
원인으로 단정하지 않는다.

## 0.2.0에서 확인한 실제 흐름

1. `App.OnStartup`이 SQLite 데이터베이스와 설정·단축어 저장소를 연다.
2. `MainViewModel.InitializeAsync`가 설정과 단축어를 읽어
   `TextExpansionService.UpdateConfiguration`에 전달한다.
3. `GlobalKeyboardHook.Start`가 UI 스레드에서
   `SetWindowsHookEx(WH_KEYBOARD_LL)`를 한 번 호출한다.
4. 후크 콜백은 키를 놓는 메시지 가운데 `Space`만 확인한다.
5. `TextExpansionService`는 70ms 뒤 백그라운드 작업에서 전경 프로세스 이름을
   구하고 제외 목록을 검사한다.
6. `WindowsInputInspector`가 포커스 요소의 UI Automation `TextPattern`으로
   캐럿 앞 문자열을 읽는다.
7. `ShortcutMatcher`가 `단축어 + 공백` 접미사를 찾는다.
8. UI Automation 선택 범위로 `단축어 + 공백`을 선택한다.
9. `UnicodeInputSender`가 `변환문 + 공백` 전체를 한 번의 `SendInput` 호출로
   입력한다.
10. 예외가 없으면 사용 횟수를 증가시키고 UI를 새로 고친다.

## 0.2.0에서 코드로 확인된 문제

| 단계 | 실제 문제 | 사용자에게 보이는 결과 |
| --- | --- | --- |
| 설정 | Enter·Tab 값은 저장되지만 UI가 비활성화되어 있고 후크가 Space만 처리한다. | Enter·Tab 설정으로는 변환되지 않는다. |
| 후크 등록 | 최초 등록 실패만 예외로 알리고 이후 생존 상태·재등록·세션 복구가 없다. | 시작 후 후크가 사라지면 앱은 실행 중처럼 보이지만 입력을 감지하지 못할 수 있다. |
| 후크 콜백 | 이벤트 처리 경로가 콜백에서 직접 호출되고 후크 핸들·스레드·마지막 수신 시각을 노출하지 않는다. | 차단과 무입력을 구분할 증거가 없다. |
| 입력 문맥 | UIA `TextPattern`이 없는 컨트롤, 접근 거부, 읽기 전용, 다중 선택 등은 모두 `false`다. | 민감 입력창·지원하지 않는 컨트롤·권한 차이가 모두 조용히 같은 실패로 끝난다. |
| 제외 정책 | 전경 프로세스 이름을 읽지 못해도 제외로 처리한다. 보호 프로세스와 사용자 제외가 같은 결과다. | 왜 차단되었는지 알 수 없다. |
| 매칭 | Space 한 문자만 종결자로 지원한다. | Enter·Numpad Enter·Tab을 구분하지 못한다. |
| 삭제 | UIA 선택에 전적으로 의존한다. | 선택 기능을 지원하지 않으면 주입 단계에 도달하지 못한다. |
| 입력 주입 | `SendInput` 한 번의 반환값만 검사하며 삭제·본문·종결자 결과를 분리하지 않는다. | 어느 단계가 실패했는지 알 수 없고 부분 실패 복구 안내가 없다. |
| 권한 | 한키와 대상의 무결성 수준을 비교하지 않는다. | UIPI 가능성을 사전·사후에 구분하지 못한다. |
| 로깅 | 예외 형식과 위치만 남긴다. | 원문은 보호되지만 현장 원인 분류에 필요한 상태도 없다. |
| 사용 횟수 | 예외가 발생하면 증가하지 않지만, 단계별 성공을 명시적으로 판정하지 않는다. | 부분 주입을 성공과 명확히 구분할 수 없다. |

PC방 증상의 직접적인 단일 원인은 아직 확인되지 않았다. 다만 0.2.0에는
후크 등록 이후 상태를 관찰할 방법이 없고, UIA가 지원되지 않거나 접근이
거부된 경우도 조용히 종료되므로 “앱과 설정은 정상인데 아무 반응이 없음”을
만들 수 있는 경로가 실제로 존재한다.

## 0.2.1 구현 흐름

아래 흐름은 `97b95bf` 이후 실제 구현을 다시 추적해 확인했다.

1. 전용 메시지 스레드에서 저수준 키보드 후크를 등록하고 핸들·스레드·등록
   시각을 상태로 보관한다.
2. 후크 콜백은 최소 키 메타데이터만 bounded 채널에 넣고 즉시 다음 후크로
   넘긴다. 입력 문자 원문은 진단 이벤트에 넣지 않는다.
3. 작업자는 Space, Enter, Numpad Enter, Tab, Backspace, 문자 후보를 구분하고
   현재 키보드 레이아웃·IME·수정키 상태를 갱신한다.
4. 기능 OFF, 일시 정지, 사용자 제외 앱·사이트, 보호 대상, 민감 입력창,
   문맥 정보 접근 불가를 서로 다른 내부 사유로 판정한다.
5. UIA 문맥을 사용할 수 있으면 단축어 후보를 메모리에서만 검사한다.
   원문 키·문장·클립보드·창 제목은 이벤트나 보고서에 기록하지 않는다.
6. 한키와 대상 프로세스의 무결성 수준을 비교해 높은 권한 대상 또는 정보
   접근 거부를 별도 상태로 표시한다.
7. 직접 입력 모드는 다음 단계를 각각 한 번만 수행하고 요청/성공 이벤트
   수를 기록한다.
   - 단축어와 이미 입력된 종결자 삭제
   - 변환문 Unicode 입력
   - 선택한 종결자 재입력
8. 세 단계가 모두 성공한 경우에만 사용 횟수를 증가시킨다. 일부 실패는
   성공으로 집계하지 않고 자동 무한 재시도도 하지 않는다.
9. 사용자가 명시적으로 켠 경우에만 클립보드 붙여넣기 호환 모드를 사용한다.
   민감·제외 대상에서는 사용하지 않으며, 클립보드 시퀀스가 바뀌면 기존
   내용을 강제로 덮어쓰지 않는다.
10. 구조화 진단은 최근 200개 이벤트만 메모리에 보관한다. 사용자가 내보내기
   버튼을 누를 때 안전한 JSON·TXT와 ZIP을 만든다.

## 개인정보 경계

진단에 허용되는 값은 UTC 시각, 앱·Windows 버전, 프로세스 파일명(경로 제외),
무결성 수준, 키보드 레이아웃 식별자, IME 열림 여부, 종결자 종류, 단계별
요청/성공 개수, 열거형 차단·오류 사유, 단축어의 비가역 임의 ID뿐이다.

다음 값은 메모리의 순간 매칭 처리 밖으로 내보내지 않는다.

- 사용자가 누른 문자와 전체 키 입력
- 단축어 원문과 변환문 원문
- 클립보드 내용
- 문서 내용과 전체 창 제목
- 사용자 이름, 이메일, 전체 파일 경로
- 비밀번호·전화번호 등 민감 입력 데이터

## 실패 분류 원칙

- `HookRegistrationFailed`와 최근 콜백 없음은 “보안 프로그램이 차단했다”가
  아니라 각각 관찰된 사실과 가능성으로 표시한다.
- `TargetHigherIntegrity`는 UIPI에 의한 주입 제한 가능성이 높다는 뜻이며
  `SendInput`의 마지막 오류 코드만으로 확정하지 않는다.
- `SensitiveField`, `ExcludedApplication`, `ProtectedTarget`,
  `InputContextUnavailable`은 서로 바꾸어 기록하지 않는다.
- 게임·안티치트·PC방 보안 정책을 우회하지 않는다. 관리자 재시작은 사용자가
  직접 누른 현재 세션용 선택 기능이며 기본 동작이나 보장책이 아니다.
